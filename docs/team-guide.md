# 팀 지침서

3명 모두가 같은 방식으로 일하기 위한 문서입니다. 처음 읽을 때는 1~5장만 읽어도 시작할 수 있어요.

## 1. 우리 프로젝트 한 줄

숨은 캐릭터를 YOLO가 찾아내고, **얼마나 잘 숨었는지 점수**로 보여주는 미니게임입니다.
처음엔 아주 작게(자세 1개, 박스 라벨만) 시작해서 끝까지 한 바퀴 도는 것이 목표예요.

## 2. 누가 무엇을 하나

| 이름 | 역할 | 만드는 것 | 내 폴더 | 내 브랜치 |
|---|---|---|---|---|
| 이한울 | 모델 | 데이터로 YOLO 학습, 이미지를 넣으면 박스·신뢰도를 주는 `detect()` | `src/model/` | `yolo/model` |
| 이상현 (조장) | 점수·백엔드 | 탐지 결과를 점수로 바꾸는 `evaluate()`, 문서·일정 관리 | `src/score/` | `score/algorithm` |
| 한승우 | UI·통합 | 입력 → 결과 화면, 세 모듈을 하나로 연결 | `src/ui/` | `ui/merge` |

각자 **자기 폴더만** 수정하면 충돌이 거의 생기지 않습니다.
README, `requirements.txt` 같은 공용 파일을 바꿀 때는 PR 설명에 적어 주세요.

## 3. 실습실에서 시작할 때 체크리스트

실습실은 매번 환경을 새로 만들어야 하므로 아래 순서대로 합니다.

- [ ] 레포 clone (이미 있으면 `git pull`)
- [ ] 가상환경 만들고 활성화
- [ ] `pip install -r requirements.txt`
- [ ] Drive에서 필요한 데이터·모델 가중치를 `data/`로 내려받기
- [ ] 내 브랜치로 이동

```bash
git clone https://github.com/sh-lee-dev/meccha-finder.git
cd meccha-finder
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
git checkout <내 브랜치>
```

끝날 때는 **커밋 + 푸시**를 꼭 하세요. 실습실 PC에 남겨둔 파일은 다음에 사라질 수 있습니다.

## 4. 하루 작업 흐름

```bash
# 1) 내 브랜치에서 작업하고 커밋
git add .
git commit -m "feat(score): 점수 함수 v0 추가"

# 2) PR 올리기 전에 최신 main을 내 브랜치에 병합
git fetch origin
git merge origin/main

# 3) 푸시
git push origin <내 브랜치>

# 4) GitHub에서 Pull Request 생성 → 다른 팀원 1명 이상 확인 → Squash and merge
```

## 5. Git 규칙

| 규칙 | 내용 |
|---|---|
| 브랜치 구조 | 각자 브랜치에서 작업하고 PR로 main에 병합 (수평형) |
| 금지 | `rebase`, `git push --force` (실수하면 복구가 어려움) |
| 최신화 | PR 전에 `origin/main`을 내 브랜치에 병합 |
| 병합 방식 | Squash and merge (내 브랜치 커밋이 지저분해도 괜찮음) |
| main 직접 푸시 | 하지 않기 |
| 커밋 메시지 | `feat` 기능, `fix` 수정, `docs` 문서, `data` 데이터 관련. 예: `fix(model): 라벨 경로 오류 수정` |
| 올리지 않는 것 | 데이터셋, 영상, 모델 가중치(`.pt`), 가상환경 폴더 |

충돌이 났을 때는 혼자 해결하려 하지 말고 팀 채팅에 먼저 공유하세요.

## 6. 모듈 간 입출력 약속

세 모듈이 서로 기다리지 않고 개발하려면 **주고받는 형식**을 먼저 맞춰 둬야 합니다.
아래는 초안이며, 1주차에 확정합니다. 바꿀 때는 3명 모두에게 알립니다.

**모델 → 점수** (`src/model`의 `detect`)

```python
def detect(image_path: str) -> dict:
    ...

# 반환 예시
{
    "found": True,                     # 못 찾으면 False
    "bbox": [x1, y1, x2, y2],          # 픽셀 좌표, found가 False면 None
    "confidence": 0.82,                # 0~1, found가 False면 0.0
    "image_size": [width, height],
}
```

**점수 → UI** (`src/score`의 `evaluate`)

```python
def evaluate(detection: dict, elapsed_sec: float | None = None) -> dict:
    ...

# 반환 예시
{
    "total": 78,                       # 0~100
    "axes": {"축 이름": 70, ...},       # 능력치 차트용, 축은 2주차 확정
    "comments": ["기준별 한 줄 코멘트", ...],
}
```

**개발 중에는 더미 데이터를 써서** 서로의 완성을 기다리지 않습니다.
(예: UI 담당은 위 반환 예시를 그대로 가짜 데이터로 사용)

## 7. Google Drive 사용법

문서는 두 곳에 나눠서 둡니다.

| 위치 | 두는 것 | 기준 |
|---|---|---|
| GitHub `docs/` | README, 요구사항, 결정 기록, 이 지침서 | 코드와 함께 바뀌거나, 레포를 처음 보는 사람이 알아야 하는 것 |
| Google Drive | WBS, 주간 진행상황, 회의록, 데이터, 모델 가중치, 결과물 | 자주 바뀌거나, 팀 내부용이거나, 용량이 큰 것 |

Drive 공유 폴더 구조는 아래와 같습니다.

```
meccha-finder/
├── 00_안내/            Drive 사용 규칙, GitHub 레포 링크, 자주 쓰는 링크 모음
├── 01_일정·진행/        WBS (Google Sheets), 주간 진행상황
├── 02_회의록/           2026-11-11_킥오프 형식으로 날짜를 앞에
├── 03_data/
│   ├── raw_videos/      원본 영상 (외부 공유 금지)
│   ├── frames/          영상별 하위 폴더 (play01/, play02/ ...)
│   ├── labels/          라벨링 결과 (YOLO .txt)
│   └── datasets/        분할 완료본 (dataset_v1/, dataset_v2/ ...)
├── 04_models/           best_v1_20261118.pt + 학습 설정·결과 메모
├── 05_결과물/           데모 스크린샷, GIF
├── 06_참고자료/          논문, 블로그, 공식 문서 링크
└── 개인별/              상현/, 승우/, 한울/ (실험·메모용 작업 공간)
```

- 파일을 덮어쓰지 말고 **버전을 이름에 붙여** 새로 올립니다 (`dataset_v2`, `best_v2_...`).
- 데이터셋을 새로 만들면 팀 채팅에 버전과 변경 내용을 한 줄 남깁니다.
- `개인별/`에서 만든 결과 중 다른 사람도 써야 하는 것은 공용 폴더로 옮깁니다.
- 원본 영상과 프레임은 외부에 공유하지 않습니다.
- **Drive 공유 링크는 레포에 적지 않습니다.** 레포가 공개되면 누구나 원본 영상에 접근할 수 있으므로, 링크는 `00_안내`와 팀 채팅에만 둡니다.
- 내려받은 데이터는 레포의 `data/` 폴더에 두면 됩니다 (Git 제외 폴더).

## 8. 앞으로 어떻게 개발하나

| 단계 | 하는 일 | 끝났다는 기준 |
|---|---|---|
| 1단계 (1주차) | 환경·규칙 정리, 작은 데이터 준비, 입출력 약속 확정 | 라벨링된 데이터와 입출력 약속이 준비된다 |
| 2단계 (2주차) | 첫 학습, 모듈별 v0를 더미 데이터로 단독 실행 | 이미지 1장에서 박스와 신뢰도가 나온다 |
| 3단계 (3주차) | 세 모듈을 연결, 데이터 확장 | 입력 → 탐지 → 점수 → 화면이 끝까지 된다 |
| 4단계 (4주차) | 성능·점수 다듬기, 차트, 포트폴리오 정리 | 최종 데모 |

작은 범위로 끝까지 돌려 본 뒤에 넓히는 것이 원칙입니다.
(자세와 배경을 늘리고, 여유가 있으면 윤곽선, 모델 보조 라벨링, 다중 캐릭터로 확장)

세부 일정은 Drive의 WBS 시트, 요구사항은 [requirements.md](requirements.md)를 보세요.

## 9. 소통과 기록

- 주 1회 짧은 싱크 미팅(15분 내외)에서 진행상황, 막힌 점, 다음 주 할 일을 확인합니다.
- 각자 맡은 작업의 상태는 Drive WBS 시트의 상태 열에서 직접 바꿉니다.
- 조장이 Drive의 주간 진행상황을 주 1회 갱신합니다.
- 결정한 내용은 말로만 두지 말고 [decisions.md](decisions.md)에 남깁니다.
- 막히면 30분 이상 혼자 붙잡지 말고 바로 공유합니다.

## 10. 자주 묻는 질문

**Q. main에 이미 있는 변경 때문에 PR이 막혀요.**
A. `git fetch origin` 후 `git merge origin/main`으로 최신 main을 내 브랜치에 합친 뒤 다시 푸시하세요.

**Q. 실수로 데이터나 `.pt` 파일을 커밋했어요.**
A. 푸시 전이면 팀 채팅에 알리고 같이 정리합니다. 푸시했다면 혼자 force push 하지 말고 조장에게 바로 알려 주세요.

**Q. 다른 사람 폴더의 코드를 고치고 싶어요.**
A. 직접 고치지 말고 그 담당자에게 요청하거나 PR 코멘트로 제안해 주세요.
